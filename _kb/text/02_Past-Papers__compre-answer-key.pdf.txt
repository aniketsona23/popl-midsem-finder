The difference between an REPL and an event-loop:
The former is a CLI shell
like Python (or GNU Octave, Lisp, Jupyter notebook, etc.). The latter is a GUI with
windows, menus, buttons, switches, pop-ups, textbox inputs, etc. For example, one could
provide an asynchronous interface with input and keyword files independently read and
changed, merged, extracted, etc.

2. Justification If they had identified their top level interface and justified it in their report

give 1; otherwise 0.
3. Paradigm An REPL is either Pure Functional or (more likely) Functional OO. An event loop
is Functional-OO. In both the cases, computation proceeds asynchronously (or in a stimulus-
response reactive manner) not procedurally. Any other top-level interface, especially the more
common text-menu-driven CLI that most students provided, is Modular-OO or just Procedu-
ral. In this case, computation proceeds via a single interactive thread with the startup main
is always in control and the user guides each step.
Answer3.
The main difference between the two kinds of implementations is the interaction
of the logical operation of partitioning with the storage structure operations. The Python
implementation is not in place, it creates a new part each for the left and the right parts
of the partition by a map-filter, and then concatenates them into a new list. The usual
C, C++, Java implementations perform in place swaps partitioning the same array
without copying.
(i) Surely the usual non-Python implementations are all more efficient because they de-
pend on indexed access to arrays and no unnecessary copying (only necessary swaps).
(ii) Similarly, the usual non-Python implementations all use constant extra space (1 tem-
porary element for swaps), thus more space-efficient.
(iii) Of course Python is more versatile, type-flexible, since it is dynamically typed.
(iv) Assuming that the implementation of the map-filter for loop in Python scans the array
left-to-right and copies into the new array in the same order, it is stable. The usual
Lomuto-partitioning is not stable inherently. (Hoare partitioning too.)
(v) The given Python implementation is not suitable for any large array even if all of it
fits into the main memory at once. Because it doesn’t do in-place sorting. It needs two
copies of the array in each iteration. The usual implementations are suitable for this.
In fact that is why quicksort implemented in C-style is the most common algorithm
used for any infrastructure sort utility on all platforms, or embedded in large software
packages like spreadsheet editors.
